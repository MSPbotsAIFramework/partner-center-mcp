## Product design

### Goals / Non-goals

**Goal**: an MSPbots agent can call a new MCP tool, `csp_update_customer_subscription_quantity`, exposed by `partner-center-mcp`, to change the license quantity on an existing Partner Center subscription for a given CSP customer tenant, and get back the updated quantity and status — replacing the Rewst "MS Tier 1: Purchase Licence" flow for Ginko IT and EMD Networking Services.

**Non-goals** (separate tickets or out of scope):
- Listing a customer's subscriptions — PRD-21573.
- Listing the partner's customers — PRD-21603.
- Creating a brand-new subscription (a Partner Center "purchase") — the ticket and the Rewst action it replaces only change the quantity on an *existing* subscription.
- Any `agent.mspbots.ai` UI change — this is a backend MCP tool with no UI surface of its own; wiki coverage is the connector doc, handled after INT publish (see Rollout).
- Acquiring or refreshing the underlying Partner Center OAuth token on the partner's behalf — inherited from PRD-21573's credential-model decision (Current state above).
- Any quantity-change business rule Partner Center itself enforces (minimum commitment, proration, billing impact) — this tool passes the requested quantity through and surfaces whatever Partner Center decides; it does not pre-validate against commercial rules.

### Acceptance criteria AC1..AC9

- **AC1 (happy path)**: Given a valid `X-PartnerCenter-Token` header, an existing `customer_tenant_id`, an existing `subscription_id` on that tenant, and a new `quantity` that is a positive integer, When `csp_update_customer_subscription_quantity` is called, Then the tool GETs the current subscription, PATCHes it back with only `quantity` changed, and returns `{id, quantity, status}` reflecting Partner Center's post-update state.
- **AC2 (missing credential)**: Given a request to any tool on this server has no `X-PartnerCenter-Token` header, When the tool is invoked, Then the server returns 401 with a structured body naming the required header, and no call reaches Partner Center (shared middleware behavior, same as PRD-21573 AC2).
- **AC3 (missing required argument)**: Given `customer_tenant_id`, `subscription_id`, or `quantity` is omitted or (for the two string arguments) blank, When the tool is called, Then the tool returns a structured `invalid_argument` error and makes no Partner Center API call (neither GET nor PATCH).
- **AC4 (invalid quantity value)**: Given `quantity` is present but is negative or not an integer, When the tool is called, Then the tool returns a structured `invalid_argument` error and makes no Partner Center API call. (Zero is allowed through to Partner Center — see Open questions; Partner Center's own validation, not this tool, is the authority on whether a given offer permits 0.)
- **AC5 (unknown tenant or subscription)**: Given `customer_tenant_id` or `subscription_id` does not exist (or the partner has no active reseller relationship with that tenant), When the tool is called, Then the initial GET fails and the tool returns a structured error (`not_found` or `unauthorized`, matching whichever status Partner Center actually returns) — no PATCH is attempted.
- **AC6 (unauthorized)**: Given the token's partner has no active reseller relationship with the tenant (GET or PATCH returns 401/403), When the tool is called, Then the tool returns a structured `unauthorized` error carrying the upstream message, not a raw 500.
- **AC7 (GET succeeds, PATCH rejected)**: Given the GET returns the current subscription successfully but the subsequent PATCH is rejected by Partner Center (e.g. a business-rule violation such as a quantity below the offer's minimum commitment, surfaced as 400/409/422), When the tool is called, Then the tool returns a structured error carrying the upstream PATCH failure — the response never claims success, and no partial/ambiguous state is reported, even though the GET itself succeeded.
- **AC8 (upstream failure surfaced)**: Given Partner Center returns a 5xx or times out on either the GET or the PATCH call, When the tool is called, Then the tool retries that call (capped, exponential backoff, honors `Retry-After`) and, if still failing, returns a structured `upstream_error` marked retryable — not a stack trace, a raw 500, or a silently-empty success.
- **AC9 (multi-tenant isolation)**: Given two concurrent calls updating subscriptions for two different customer tenants using two different partner tokens, When both run concurrently, Then each call's GET and PATCH use only its own call's token and ids — no credential, tenant id, or subscription id crosses between the two calls.

### Open questions

- [已假设] Whether `quantity: 0` is a valid request for every Partner Center offer type is not something this tool decides — it is passed through to the PATCH call and Partner Center's own validation is authoritative (rejected upstream calls map to AC7's `invalid_argument`/upstream-error path, not a client-side pre-check). If this is wrong and the organization wants this tool itself to block `quantity: 0` as a product policy (e.g. "use a cancellation flow instead"), AC4 and the validation in Tech design §4 need a lower bound of 1 instead of 0.
- [不阻塞] Partner Center's exact error-body shape for the PATCH failure case (AC7) is taken from the publicly documented reference, not verified against a live call (no test account, same limitation as PRD-21573). Dev leg confirms during implementation; only the internal parser changes if the shape differs, the external MCP error envelope (`{error: {code, message, retryable}}`) does not.
- [已假设] This design assumes, like PRD-21573, that the gateway/connector layer is responsible for obtaining and refreshing the Partner Center App+User access token and forwards only the resulting bearer token to this service. This ticket does not re-litigate that decision (see Current state); if the assumption is wrong for the connector as a whole, it is PRD-21573's design that needs to change, and this ticket's tool inherits whatever credential contract results.
- [不阻塞] Whether the shared scaffold will already exist on `main` when this ticket's dev leg starts depends on which of the three sibling tickets' dev legs runs first — not a product question, see Tech design §4/§Risks for how the design handles either ordering.

## Tech design

### Conclusion

Add one tool, `csp_update_customer_subscription_quantity`, to the shared `partner-center-mcp` scaffold that PRD-21573 already designed (same credential middleware, same HTTP client conventions, same `csp_` tool prefix — not re-decided here). The tool does a read-modify-write: `GET /customers/{tenant}/subscriptions/{subscription_id}` to fetch the current resource, set `quantity` to the requested value, `PATCH` the same path with the full modified resource (Partner Center's PATCH contract requires the complete resource body, not a sparse patch — Current state above), and maps the result to `{id, quantity, status}`. If this ticket's dev leg runs before any sibling's, it builds the shared scaffold (identical to PRD-21573's Change list) in addition to this tool; if a sibling's dev leg has already merged the scaffold into `main`, this ticket only adds the new tool function and the `api_client.py` `patch()` method. No new architectural pattern is invented — the write-tool shape (argument validation → upstream call → structured error envelope) is copied from `ms-graph-mcp`'s `graph_assign_license`.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A: GET-then-PATCH with the full resource body (per Microsoft's documented contract) | Fetch the current subscription, mutate only `quantity` locally, PATCH the whole object back | Matches the vendor's actual documented contract for this endpoint exactly; ticket description itself specifies this flow ("先 GET 原对象再改 quantity 回写"); no risk of accidentally clobbering other fields (`offerId`, `friendlyName`, etc.) since they are round-tripped unchanged | Two upstream calls instead of one (GET + PATCH); a window exists between GET and PATCH where another caller could change the subscription first (no optimistic-concurrency / ETag mechanism is documented for this endpoint) — see Risks | **Chosen** |
| B: PATCH with only `{"quantity": N}` as the body (sparse patch) | Send a minimal body, relying on the server to merge | Simpler, one call, no read-modify-write race window | Contradicts Microsoft's documented contract for this specific endpoint (it expects the full resource); risks the PATCH being silently misapplied or rejected by Partner Center, which is exactly the class of bug a design review would catch late | Not chosen — does not match the vendor's actual API contract |
| C: Pre-validate the new quantity against the offer's commitment rules before calling Partner Center | This tool fetches offer metadata and checks commitment/minimum-quantity rules locally before attempting the PATCH | Could return a clearer client-side error for some invalid requests | Requires fetching and correctly interpreting offer-specific commercial rules this tool has no documented, versioned contract for; duplicates validation Partner Center already performs server-side (AC7); scope creep beyond "update a subscription's quantity" | Not chosen — AC7's upstream-error path already covers this without needing a second source of truth for commercial rules |

### Data & API contract

**MCP tool**: `csp_update_customer_subscription_quantity`

Request (MCP tool call arguments):
```json
{"customer_tenant_id": "11111111-2222-3333-4444-555555555555", "subscription_id": "abc123", "quantity": 30}
```
- `customer_tenant_id`: required, string (the customer's Entra tenant GUID — Rewst's `ORG.MAPPING.ms_tenant_id`).
- `subscription_id`: required, string (Partner Center subscription id, e.g. from `csp_list_customer_subscriptions`'s `id` field).
- `quantity`: required, integer, ≥ 0 (no client-side upper bound — Partner Center's own commitment rules are authoritative, AC7).

Success response:
```json
{"id":"abc123","quantity":30,"status":"active"}
```

Error response (`error_envelope`, same shape as every other tool on this server, per PRD-21573's contract):
```json
{"error":{"code":"not_found","message":"<upstream message or validation message>","retryable":false}}
```
`code` ∈ `{invalid_argument, unauthorized, not_found, rate_limited, upstream_error}`; `retryable` is `true` only for `rate_limited`/`upstream_error`.

**Upstream Partner Center calls**:
1. `GET {partner_center_base_url}/customers/{customer_tenant_id}/subscriptions/{subscription_id}`, header `Authorization: Bearer <token forwarded from X-PartnerCenter-Token>`. Expected success body per Microsoft's documented reference: the full subscription resource (`id`, `offerId`, `offerName`, `friendlyName`, `quantity`, `unitType`, `billingType`, `status`, `commitmentEndDate`, ...).
2. `PATCH {partner_center_base_url}/customers/{customer_tenant_id}/subscriptions/{subscription_id}`, same `Authorization` header, body = the object from step 1 with only `quantity` replaced. Expected success body: the updated resource, same shape as step 1.

**Credential header contract**: unchanged from PRD-21573 — `X-PartnerCenter-Token` (required on every `/mcp` request).

**DB**: none — stateless, same as every other connector in the org.

**Backward compatibility**: not applicable — new tool, no prior callers.

### Decisions made by DEV01

- **Read-modify-write (GET then PATCH the full resource), not a sparse PATCH body.** Why: Microsoft's documented contract for `update-a-subscription-by-id` expects the complete resource representation back, and the ticket's own description already specifies this flow. Alternative not chosen: sending `{"quantity": N}` alone (Option B above) — contradicts the vendor's documented contract.
- **No client-side upper bound on `quantity`; lower bound is 0, not 1.** Why: no commitment-minimum rule is documented as universal across Partner Center offer types, and this service does not fetch offer metadata to know an offer-specific minimum; Partner Center's own validation is treated as authoritative (AC7 covers its rejection). Alternative not chosen: hardcoding a minimum of 1 — would reject a legitimate request for an offer type that does permit 0, without this service having the information to know which offer types those are (flagged as an assumption in Open questions, not a blocking one).
- **This ticket's tool is added to PRD-21573's `tools/subscriptions.py` module, not a new file.** Why: both tools act on the same Partner Center resource (subscriptions), matching the one-module-per-resource convention already used by `connectsecure_mcp/tools/company.py`. Alternative not chosen: a separate `tools/subscription_updates.py` — would split one resource's tools across two files for no benefit and complicate the dev-lock coordination between the two tickets' dev legs.
- **This ticket does not re-decide the credential model or tool-name prefix.** Both were already decided by PRD-21573 (Current state above) and apply to the whole connector, not per-tool; re-deciding them here per-ticket would risk the three sibling tools disagreeing with each other.

### Key flow / sequence

```
Agent -> Gateway -> (HTTP, X-PartnerCenter-Token header) -> partner-center-mcp
  csp_update_customer_subscription_quantity(customer_tenant_id, subscription_id, quantity)
    -> validate customer_tenant_id, subscription_id non-blank; quantity is an integer >= 0
         +- any invalid -> error_envelope(invalid_argument), no upstream call
    -> PartnerCenterClient.get(f"/customers/{customer_tenant_id}/subscriptions/{subscription_id}")
         -> GET {base}/customers/{tenant}/subscriptions/{subscription_id}, Authorization: Bearer <token>
         +- 401/403 -> error_envelope(unauthorized), stop (no PATCH)
         +- 404     -> error_envelope(not_found), stop (no PATCH)
         +- 429/5xx/timeout -> retry (<=3, backoff, honors Retry-After) -> still failing -> error_envelope(rate_limited|upstream_error, retryable=true), stop
         +- 2xx -> current subscription object
    -> set current["quantity"] = quantity (every other field unchanged)
    -> PartnerCenterClient.patch(f"/customers/{customer_tenant_id}/subscriptions/{subscription_id}", current)
         -> PATCH {base}/customers/{tenant}/subscriptions/{subscription_id}, Authorization: Bearer <token>, body=current
         +- 400/409/422 -> error_envelope(invalid_argument|unauthorized|not_found, matching status) -- GET having succeeded does not change this
         +- 429/5xx/timeout -> retry (<=3, backoff) -> still failing -> error_envelope(upstream_error, retryable=true)
         +- 2xx -> updated subscription object
    -> map to {id, quantity, status}
    -> dump_json_capped(...)
```

### Non-functional

- **Idempotency/concurrency**: the tool is idempotent in the sense that calling it twice with the same `quantity` converges to the same end state, but the GET-then-PATCH sequence has a window where a concurrent change to the same subscription (by another caller, or a human in the Partner Center portal) between this tool's GET and PATCH would be silently overwritten by this tool's PATCH, since Partner Center's documented contract for this endpoint carries no optimistic-concurrency token (e.g. ETag/If-Match) to detect that — flagged as a Risk below, not fixed in this design (no such mechanism exists to use).
- **Performance**: two sequential upstream calls per tool call (GET then PATCH), no fan-out; response capped at 20,000 chars by `dump_json_capped` (a single subscription object is far under that). No load/concurrency requirement was stated in the ticket, so no performance-specific test case is produced.
- **Security**: credential never persisted — `X-PartnerCenter-Token` lives only in the per-request `contextvars.ContextVar` (shared middleware), never logged, never written to disk or env; missing header is rejected before any upstream call (AC2); this service never holds the Client Secret or Refresh Token used upstream of it. This tool performs a billing-relevant write (changing a paid license count) — the structured error contract (AC7) ensures a rejected or failed write is never reported as success.
- **Multi-tenant isolation**: token, `customer_tenant_id`, and `subscription_id` are all function-local to a single call; the shared `httpx.AsyncClient` pool (per the scaffold's convention) holds no per-call state; two concurrent calls cannot observe each other's token, tenant, or subscription id (AC9) — same isolation mechanism as every other connector in the org.
- **Observability**: failures return a structured `error_envelope` with enough detail (code + upstream message) to locate the cause without needing server-side logs; no new logging infrastructure is added, and request/response bodies (which could contain tenant-identifying data) are not logged, consistent with the sibling design.

### Risks & dependencies

- **Dependency**: shared repo with PRD-21573 and PRD-21603, coordinated via the repo's `dev-lock`; whichever of the three reaches the dev leg first builds the scaffold, the other two add their own tool module/function onto it (same dependency PRD-21573 records).

- **Risk**: the GET-then-PATCH sequence has a race window — if another caller (or a human in the Partner Center portal) changes the subscription between this tool's GET and PATCH, this tool's PATCH will overwrite that change with a resource object built from the now-stale GET, because Partner Center's documented contract for this endpoint has no ETag/If-Match mechanism to detect it. Mitigation: none available within this tool's contract; if MSPbots later needs stronger consistency, it would require Microsoft to document an optimistic-concurrency mechanism for this endpoint that does not currently exist.
- **Risk**: Partner Center's upstream error-body shape for the PATCH failure case is taken from public documentation, not verified live; if it differs, only the internal message-extraction in `api_client.py` needs adjusting, not the external MCP error contract (same mitigation already used by the connectsecure-mcp precedent's best-effort message-field fallback chain).
- **Risk**: this design assumes the gateway/connector layer owns the Partner Center App+User OAuth exchange and only forwards a ready bearer token to this service (inherited from PRD-21573). If that assumption does not hold, the credential-header contract needs to be redone connector-wide before any of the three tools can go live, and this ticket's Story Point estimate would need to go up along with the other two.
