## Product design

### Goals / Non-goals

**Goal**: an MSPbots agent can call a new MCP tool, `csp_list_customer_subscriptions`, exposed by `partner-center-mcp`, and get back the list of Partner Center subscriptions for a given CSP customer tenant, with the fields the Rewst flows it replaces actually use: id, offer name, quantity, status, billing cycle, unit type, commitment end date.

**Non-goals** (separate tickets or out of scope):
- Updating a subscription's quantity — PRD-21574.
- Listing the partner's customers — PRD-21603.
- Any `agent.mspbots.ai` UI change — this is a backend MCP tool with no UI surface of its own; wiki coverage is the connector doc, handled after INT publish (see Rollout).
- Acquiring or refreshing the underlying Partner Center OAuth token on the partner's behalf — see Tech design §1 and §Decisions.
- Pagination beyond a safety cap (§ below) — Partner Center's subscriptions endpoint is not documented as paginated; see Tech design §4a.

### Acceptance criteria AC1..AC8

- **AC1 (happy path)**: Given a valid `X-PartnerCenter-Token` header and a `customer_tenant_id` with active subscriptions, When `csp_list_customer_subscriptions` is called, Then the tool returns `items` with one entry per subscription containing `id`, `offer_name`, `quantity`, `status`, `billing_cycle`, `unit_type`, `commitment_end_date`, plus `total_count` and `has_more`.
- **AC2 (missing credential)**: Given a request to any tool on this server has no `X-PartnerCenter-Token` header, When the tool is invoked, Then the server returns 401 with a structured body naming the required header, and no call reaches Partner Center.
- **AC3 (missing required argument)**: Given `customer_tenant_id` is omitted or blank, When `csp_list_customer_subscriptions` is called, Then the tool returns a structured `invalid_argument` error and makes no Partner Center API call.
- **AC4 (unknown/unauthorized customer tenant)**: Given `customer_tenant_id` does not exist, or the partner identified by the token has no active reseller relationship with that tenant, When the tool is called, Then the tool returns a structured error (`not_found` or `unauthorized`, matching whichever status Partner Center actually returns) carrying the upstream message, not a raw 500.
- **AC5 (empty result)**: Given the customer tenant exists but has zero subscriptions, When the tool is called, Then the tool returns `items: []`, `total_count: 0`, `has_more: false` — this is success, not an error.
- **AC6 (truncation)**: Given Partner Center reports more subscriptions than the effective `limit`, When the tool is called, Then the response contains at most `limit` items (default 50, hard cap 200) and `has_more: true`.
- **AC7 (multi-tenant isolation)**: Given two concurrent calls for two different customer tenants using two different partner tokens, When both run concurrently, Then each response reflects only its own call's token and tenant — no credential or data crosses between the two.
- **AC8 (upstream failure surfaced)**: Given Partner Center returns a 5xx or times out, When the tool is called, Then the tool returns a structured `upstream_error` marked retryable, not a stack trace, a raw 500, or a silently-empty success.

- [已假设] This design assumes the gateway/connector layer is responsible for obtaining and refreshing the Partner Center App+User access token, and forwards only the resulting bearer token to this service (same shape as `ms-graph-mcp`'s `X-Ms-Graph-Token`) — see Tech design §1/§Decisions for why. If that assumption is wrong and this service must itself perform the App+User refresh-token exchange, Tech design §4a's credential-header contract needs to be redone (accept Client ID/Secret/Tenant/RefreshToken headers and add a token-exchange call), which would also raise the Story Point estimate.

## Tech design

### Conclusion

Build the first version of `partner-center-mcp`: the shared package scaffold (FastMCP server, single-header credential middleware, HTTP client, Dockerfile, tests, README) that does not exist yet, plus one tool, `csp_list_customer_subscriptions`, that calls `GET {base}/customers/{customer_tenant_id}/subscriptions` and returns the seven fields the ticket asks for. ### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A: single-header token passthrough (like `ms-graph-mcp`) | This service holds no Partner Center credentials; it expects an already-valid access token per request via `X-PartnerCenter-Token` and only forwards it | Matches SOP laws (§3.3/§3.4: credentials only from Header, no cross-request cache, true statelessness) with zero extra machinery; identical shape to the connector's existing OAuth-app credential variant (`_connector-fields.md` § 变体 2), which already assumes the gateway/connector layer owns the OAuth dance | This service cannot itself verify the token is for the right resource/scope before calling Partner Center — relies on the caller having obtained a correctly-scoped token | **Chosen** |
| B: accept Client ID / Client Secret / Tenant ID / Refresh Token headers, exchange for an access token on every call | This service performs the App+User refresh-token grant against `login.microsoftonline.com` itself, per request | No change needed on the gateway/connector side for this one vendor | Either re-exchanges on every single tool call (extra Microsoft round trip + exposure to Microsoft's own throttling, on top of Partner Center's own rate limits) or caches the derived access token across requests — the latter is exactly what SOP §3.4 forbids ("不跨请求缓存...派生 token"); also duplicates OAuth-refresh logic the connector/gateway layer already owns for every other OAuth-app-style vendor | Not chosen — violates the no-cross-request-token-cache rule or pays a Microsoft round trip per call |
| C: have this service also implement the one-time App+User admin-consent flow (authorization URL + refresh-token capture) | Full self-contained onboarding | Partners could connect without any gateway-side special-casing | Scope far beyond "list subscriptions"; this is connector/gateway product surface (how a tenant connects a new vendor), not a vendor MCP tool; no other MSPbots vendor MCP repo does this | Not chosen — out of scope for a vendor MCP service |

### Data & API contract

**MCP tool**: `csp_list_customer_subscriptions`

Request (MCP tool call arguments):
```json
{"customer_tenant_id": "11111111-2222-3333-4444-555555555555", "limit": 50}
```
- `customer_tenant_id`: required, string (the customer's Entra tenant GUID — Rewst's `ORG.MAPPING.ms_tenant_id`).
- `limit`: optional, integer, default 50, hard cap 200 (clamped, never rejected for being "too high" — just capped).

Success response:
```json
{"items":[{"id":"abc123","offer_name":"Microsoft 365 Business Premium","quantity":25,"status":"active","billing_cycle":"monthly","unit_type":"Licenses","commitment_end_date":"2027-03-01T00:00:00Z"}],"total_count":1,"has_more":false}
```

Error response (`error_envelope`, same shape for every failure branch):
```json
{"error":{"code":"not_found","message":"<upstream message or validation message>","retryable":false}}
```
`code` ∈ `{invalid_argument, unauthorized, not_found, rate_limited, upstream_error}`; `retryable` is `true` only for `rate_limited`/`upstream_error`.

**Upstream Partner Center call**: `GET {partner_center_base_url}/customers/{customer_tenant_id}/subscriptions`, header `Authorization: Bearer <token forwarded from X-PartnerCenter-Token>`. Expected success body per the ticket's cited reference: `{"totalCount": N, "items": [{"id", "offerName", "quantity", "status", "billingCycle", "unitType", "commitmentEndDate", ...other fields not surfaced by this tool}], "links": {...}}`.

**Credential header contract**: `X-PartnerCenter-Token` (required on every `/mcp` request) — a bearer access token already issued for resource `https://api.partnercenter.microsoft.com` via the partner's own Entra ID app (App+User authentication). This service never sees the Client ID, Client Secret, Tenant ID, or Refresh Token used to obtain that token (see Decisions below).

**DB**: none — this service is stateless, same as every other connector in the org.

**Backward compatibility**: not applicable — first version of a new tool and a new repo; no prior callers to break.

### Decisions made by DEV01

- **Credential model: single-header token passthrough, not a server-side OAuth exchange.** Why: Partner Center's App+User flow needs a one-time interactively-consented refresh token and a non-standard refresh grant against `login.microsoftonline.com`; doing that inside a per-request-isolated, nothing-cached-across-requests container (SOP §3.3/§3.4) means either a Microsoft round trip on every tool call or caching a derived token across requests, and the latter is explicitly forbidden. Alternative not chosen: accept Client ID/Secret/Tenant/RefreshToken headers and exchange per call (Option B above).
- **Tool prefix stays `csp_`, not `partner_center_`.** This ticket and both siblings (PRD-21574 `csp_update_customer_subscription_quantity`, PRD-21603 `csp_list_customers`) already use `csp_` consistently in their titles, taken from the Rewst gap register. Overriding the generic "`<repo-name>_` prefix" convention here would contradict three already-agreed, explicit tool names for no benefit. Alternative not chosen: renaming to `partner_center_list_customer_subscriptions` to match the repo name exactly.
- **Response field truncation applies even though Partner Center's subscriptions endpoint is not documented as paginated.** The platform-wide "never return an unbounded list" rule is applied defensively (`limit` default 50 / hard cap 200, `has_more` flag) in case a partner has an unusually large customer with many subscriptions. Alternative not chosen: returning every item unconditionally, since `dump_json_capped` would silently truncate anyway on a large-enough response — an explicit `limit`/`has_more` contract is more predictable for the caller than relying on the generic char-budget truncator.
- **Base URL is overridable via config, defaulting to the public commercial endpoint.** No confirmed MSPbots customer needs a sovereign-cloud Partner Center endpoint today; this follows the `ms-graph-mcp` precedent of making the base URL a `Settings` field rather than a hardcoded constant, at near-zero cost.

### Key flow / sequence

```
Agent -> Gateway -> (HTTP, X-PartnerCenter-Token header) -> partner-center-mcp
  csp_list_customer_subscriptions(customer_tenant_id, limit?)
    -> validate customer_tenant_id non-blank
         +- blank -> error_envelope(invalid_argument), no upstream call
    -> PartnerCenterClient.get(f"/customers/{customer_tenant_id}/subscriptions")
         -> GET {base}/customers/{id}/subscriptions, Authorization: Bearer <token>
         +- 401/403 -> error_envelope(unauthorized)
         +- 404     -> error_envelope(not_found)
         +- 429     -> retry (<=3, backoff, honors Retry-After) -> still 429 -> error_envelope(rate_limited, retryable=true)
         +- 5xx/timeout -> retry (<=3) -> still failing -> error_envelope(upstream_error, retryable=true)
         +- 2xx -> {totalCount, items[...]}
    -> map items to {id, offer_name, quantity, status, billing_cycle, unit_type, commitment_end_date}
    -> clamp to limit (default 50, cap 200); has_more = total_count > returned_count
    -> dump_json_capped({items, total_count, has_more})
```

### Non-functional

- **Idempotency/concurrency**: `csp_list_customer_subscriptions` is a read-only `GET`, naturally idempotent; no shared mutable state is introduced (the one module-level `httpx.AsyncClient` connection pool, per the `connectsecure_mcp/api_client.py:17-24` precedent, carries no credentials).
- **Performance**: single upstream call per tool call, no fan-out; response capped at 200 items and 20,000 chars by `dump_json_capped`. No load/concurrency requirement was stated in the ticket, so no performance-specific test case is produced.
- **Security**: credential never persisted — `X-PartnerCenter-Token` lives only in the per-request `contextvars.ContextVar`, never logged, never written to disk or env; missing header is rejected before any upstream call (AC2); this service never holds the Client Secret or Refresh Token used upstream of it.
- **Multi-tenant isolation**: token and `customer_tenant_id` are both function-local to a single call; the shared `httpx.AsyncClient` pool holds no per-call state; two concurrent calls cannot observe each other's token or tenant (AC7) — same isolation mechanism as every other connector in the org (`contextvars.ContextVar`, set/reset in the middleware's try/finally).
- **Observability**: failures return a structured `error_envelope` with enough detail (code + upstream message) to locate the cause without needing server-side logs; no new logging infrastructure is added (none of the cited precedent repos log request bodies either, to avoid leaking tenant data).
