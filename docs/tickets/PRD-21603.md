## Product design

### Goals / Non-goals

**Goal**: an MSPbots agent can call a new MCP tool, `csp_list_customers`, exposed by `partner-center-mcp`, and get back the list of Partner Center customer tenants under the CSP partner identified by the caller's credential, with the fields the Rewst flow it replaces actually uses: id, company name, domain, relationship to partner.

**Non-goals** (separate tickets or out of scope):
- Listing a customer's subscriptions — PRD-21573.
- Updating a subscription's quantity — PRD-21574.
- Any `agent.mspbots.ai` UI change — this is a backend MCP tool with no UI surface of its own; wiki coverage is the connector doc, handled after INT publish (see Rollout).
- Acquiring or refreshing the underlying Partner Center OAuth token on the partner's behalf — decided once for the whole connector by PRD-21573 (§Decisions), not redecided here.
- Parsing, validating, or constructing the `$filter` expression — forwarded verbatim to Partner Center, same stance as `connectsecure-mcp`'s `condition` parameter (see Current state).
- Returning the full `companyProfile` object — only the four fields the ticket's Rewst flow actually consumes are surfaced (see Decisions).

### Acceptance criteria AC1..AC8

- **AC1 (happy path)**: Given a valid `X-PartnerCenter-Token` header and the partner has at least one customer tenant, When `csp_list_customers` is called with no arguments, Then the tool returns `items` with one entry per customer tenant containing `id`, `company_name`, `domain`, `relationship_to_partner`, plus `total_count` and `has_more`.
- **AC2 (missing credential)**: Given a request to any tool on this server has no `X-PartnerCenter-Token` header, When the tool is invoked, Then the server returns 401 with a structured body naming the required header, and no call reaches Partner Center. (Shared middleware behaviour, already specified and tested by PRD-21573 — see Test strategy; not a new behaviour this ticket introduces.)
- **AC3 (invalid pagination argument)**: Given `limit` or `offset` is negative, When `csp_list_customers` is called, Then the tool returns a structured `invalid_argument` error and makes no Partner Center API call.
- **AC4 (filter passthrough)**: Given a `filter` argument is supplied, When the tool is called, Then the upstream request includes it as the `$filter` query parameter unmodified (no parsing or validation on this service's side).
- **AC5 (unauthorized/no CSP relationship)**: Given the token's partner has no active CSP relationship, or the token is invalid/expired, When the tool is called, Then the tool returns a structured `unauthorized` error carrying the upstream message, not a raw 500.
- **AC6 (empty result)**: Given the partner has zero customer tenants, When the tool is called, Then the tool returns `items: []`, `total_count: 0`, `has_more: false` — this is success, not an error.
- **AC7 (pagination/truncation)**: Given Partner Center reports more customers than the effective `limit`, When the tool is called, Then the response contains at most `limit` items (default 50, hard cap 200) and `has_more: true`; passing `offset` advances the page and `has_more` accounts for it (`offset + returned_count < total_count`).
- **AC8 (upstream failure surfaced)**: Given Partner Center returns a 5xx or times out, When the tool is called, Then the tool returns a structured `upstream_error` marked retryable, not a stack trace, a raw 500, or a silently-empty success.

### Open questions

- [non-blocking] The exact Partner Center query-parameter names/semantics for pagination (`size` vs `limit`, whether `offset` is a record count or a page token) are taken from the ticket's own description, not verified against a live call (no test account, same constraint PRD-21573 recorded). Dev leg confirms the parameter names against Microsoft's reference during implementation; if `size`/`offset` turn out to mean something different, only `api_client.py`'s call-site parameter names change, not this tool's external contract (`limit`/`offset` on the MCP tool stay as designed).
- [non-blocking] `relationshipToPartner`'s accepted values are not enumerated anywhere this ticket could check (no SDK, no live account) — the tool passes the upstream string through unchanged rather than mapping it to an enum, same stance as `connectsecure-mcp`'s undocumented `source`/`condition` parameters (Current state).
- [assumed] Same assumption PRD-21573 made and that this ticket inherits rather than re-deciding: the gateway/connector layer obtains and refreshes the Partner Center App+User access token and forwards only the resulting bearer token via `X-PartnerCenter-Token`. If that assumption is wrong, it is wrong for the whole connector, not just this tool — redesigning it is PRD-21573's or a shared follow-up's responsibility, not this ticket's; this ticket's own contract (`csp_list_customers`'s request/response shape) is unaffected either way.

## Tech design

### Conclusion

Add one new tool, `csp_list_customers`, to the shared `partner-center-mcp` connector, on top of the first-version scaffold already designed by PRD-21573 (server, middleware, HTTP client, JSON helpers, config, Docker/package layout — not redesigned here, see Current state). The tool calls `GET {base}/customers` with optional `$filter`/pagination, maps the four fields the ticket needs, and follows the same error-envelope and truncation conventions every other tool in this repo (and this org) uses. No new architecture, no new credential model, no new error-handling mechanism — this is purely a new `tools/customers.py` module plus its registration, tests, and a README row.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A: thin tool module on the shared scaffold, pagination params passed straight through (like `connectsecure-mcp`'s `active_directory` tools) | `tools/customers.py` registers one tool, builds a `params` dict from `filter`/`limit`/`offset`, calls `client.get("/customers", params)`, maps the response | Zero new machinery; consistent with both sibling tools in this repo and the org-wide list-tool pattern; smallest possible diff | None of substance — this is the natural fit | **Chosen** |
| B: this tool performs its own pagination loop, fetching every page internally and returning the full customer list | Caller never sees `has_more`/`offset`; tool loops until Partner Center stops returning pages | Simpler contract for the caller in the common case (few customers) | Hides unbounded work and unbounded upstream call count behind one tool call; breaks the org-wide truncation/visibility convention (`dump_json_capped`, explicit `has_more`) that every other list tool follows; a partner with many customers could make one call fan out into dozens of upstream requests with no caller-visible cap | Not chosen — violates the org's explicit-pagination convention and hides cost from the caller |
| C: validate/transform `$filter` into a typed query object before forwarding | Friendlier tool signature (e.g. separate `domain_contains` parameter) | Nicer for simple cases | Partner Center's `$filter` grammar is not documented anywhere this ticket can verify (same gap as `connectsecure-mcp`'s `condition`); building a typed wrapper around an unverified grammar risks silently mistranslating valid filters | Not chosen — same reasoning as the existing `ConditionParam` precedent: pass through, don't guess a grammar |

### Data & API contract

**MCP tool**: `csp_list_customers`

Request (MCP tool call arguments, all optional):
```json
{"filter": "companyProfile/companyName eq 'EMD Networking Services'", "limit": 50, "offset": 0}
```
- `filter`: optional, string. Forwarded verbatim as the upstream `$filter` query parameter; this service does not parse, validate, or construct it.
- `limit`: optional, integer, default 50, hard cap 200 (clamped via the shared `clamp_limit`, never rejected for being "too high").
- `offset`: optional, integer, default 0. Negative values are rejected (AC3).

Success response:
```json
{"items":[{"id":"11111111-2222-3333-4444-555555555555","company_name":"EMD Networking Services","domain":"emdnetworking.onmicrosoft.com","relationship_to_partner":"none"}],"total_count":1,"has_more":false}
```

Error response (`error_envelope`, same shape as every other tool in this repo):
```json
{"error":{"code":"unauthorized","message":"<upstream message or validation message>","retryable":false}}
```
`code` ∈ `{invalid_argument, unauthorized, not_found, rate_limited, upstream_error}`; `retryable` is `true` only for `rate_limited`/`upstream_error`.

**Upstream Partner Center call**: `GET {partner_center_base_url}/customers`, query params `$filter` (optional), `size` (mapped from `limit`), `offset`, header `Authorization: Bearer <token forwarded from X-PartnerCenter-Token>`. Expected success body per the ticket's cited fields: `{"totalCount": N, "items": [{"id", "companyProfile": {"companyName", "domain", ...other fields not surfaced by this tool}, "relationshipToPartner", ...other top-level fields not surfaced by this tool}], "links": {...}}` — same envelope shape (`totalCount`/`items`/`links`) PRD-21573 already documented for the sibling `/customers/{id}/subscriptions` endpoint.

**Credential header contract**: unchanged from PRD-21573 — `X-PartnerCenter-Token`, decided once for the whole connector, not redecided per tool.

**DB**: none — stateless, same as every other connector in the org.

**Backward compatibility**: not applicable — first version of this tool; no prior callers.

### Decisions made by DEV01

- **Flatten and narrow the response to the four fields the ticket's Rewst flow actually consumes (`id`, `company_name`, `domain`, `relationship_to_partner`), not the full `companyProfile` object.** Why: the ticket's own description explicitly scopes the "return fields used by the flow" to exactly these four; `companyProfile` carries additional fields (e.g. the customer's own address, Entra tenant id under a different key) that no cited Rewst flow uses, and surfacing them would both grow every response for no current consumer and create an implicit contract this ticket has no requirement to maintain. Alternative not chosen: returning `companyProfile` unflattened (verbatim nested object) — rejected because it couples callers to Partner Center's exact nesting for fields they don't use, and because `dump_json_capped` budgets are better spent on more customer rows than on unused nested fields.
- **Pagination parameters are tool-local (`customers.py`'s own `Annotated` definitions), not added to the shared `tools/_common.py` yet.** Why: PRD-21573's own tool doesn't paginate, so centralizing now would mean writing shared code with exactly one consumer — deferred per YAGNI until a second tool in this repo actually needs the same shape (flagged above as a follow-up, not a blocker).
- **`offset` is passed through as a raw record count, not a Partner Center continuation/page token.** Why: the ticket's description states the optional parameters are literally named `$filter` / `size` / `offset`, which reads as an offset-based (not token-based) pagination scheme; this is unverified against a live account (Open questions), but designing for a token-based scheme the ticket doesn't mention would be guessing in the other direction with no more evidence.
- **No new tool-level retry/backoff/error-classification logic.** Why: `api_client.py`'s `PartnerCenterClient.get` (shared, from PRD-21573) already applies the org-wide retry/classification policy to every call through it; writing per-tool retry logic would duplicate it for no benefit.

To change any of these, say so in a comment and move the ticket back to 5b - ready for groom.

### Key flow / sequence

```
Agent -> Gateway -> (HTTP, X-PartnerCenter-Token header) -> partner-center-mcp
  csp_list_customers(filter?, limit?, offset?)
    -> validate limit/offset are not negative
         +- negative -> error_envelope(invalid_argument), no upstream call
    -> PartnerCenterClient.get("/customers", params={"$filter": filter, "size": clamp_limit(limit), "offset": offset})
         -> GET {base}/customers?..., Authorization: Bearer <token>
         +- 401/403 -> error_envelope(unauthorized)
         +- 404     -> error_envelope(not_found)
         +- 429     -> retry (<=3, backoff, honors Retry-After) -> still 429 -> error_envelope(rate_limited, retryable=true)
         +- 5xx/timeout -> retry (<=3) -> still failing -> error_envelope(upstream_error, retryable=true)
         +- 2xx -> {totalCount, items[...]}
    -> map items to {id, company_name, domain, relationship_to_partner}
    -> has_more = (offset_used + returned_count) < total_count
    -> dump_json_capped({items, total_count, has_more})
```

### Non-functional

- **Idempotency/concurrency**: `csp_list_customers` is a read-only `GET`, naturally idempotent; no new shared mutable state (reuses the same module-level `httpx.AsyncClient` pool PRD-21573's scaffold already sets up, which carries no credentials).
- **Performance**: single upstream call per tool call, no fan-out (Option B, pagination-loop, was explicitly rejected for this reason). Response capped at 200 items and 20,000 chars by `dump_json_capped`. No load/concurrency requirement was stated in the ticket.
- **Security**: credential never persisted — reuses the existing `X-PartnerCenter-Token` → `contextvars.ContextVar` flow; this tool never sees or logs the Client Secret/Refresh Token used upstream of the gateway; `filter` values (which may contain customer names/domains) are never logged, consistent with every other tool in this repo.
- **Multi-tenant isolation**: token is function-local to each call via the existing contextvar-based middleware (PRD-21573's mechanism, not re-implemented); this tool introduces no new shared state, so it inherits that isolation without a new test being required (see Test strategy).
- **Observability**: failures return the existing structured `error_envelope`; no new logging infrastructure.
